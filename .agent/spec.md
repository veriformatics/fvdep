## Intent

Provably secure dependencies. This repo is a library and automated system for building a library, that contains an ever-growing list of formal verification spec for popular dependencies. We create implementations for some of them in various languages as an example, but the idea is that with a provably secure spec, anyone can use coding agents to implement them in any way they want. We provide a workflow to help ensure that what they implement matches the spec, and a system for them to follow updates to the spec (perhaps this can be commercialized). We can also commercialize dependencies by request and creating the implementations for users. This whole system itself should be formally verified as well.

## Decisions

- Guarantee (user ruling): proof only — an implementation counts as delivered only with a machine-checked proof against its spec. Differential checks vs the spec oracle = development evidence, never a delivery label.
- Foreign-language route (user ruling, r1): Lean via C library only — the proven Lean implementation, compiled to a C-ABI library, linked into Rust, Python, Node, …; no per-language proof tools (Aeneas, Verus). Trusted base beyond the kernel = Lean compiler + runtime + the binding glue, stated wherever delivery is claimed.
- Security bar (user ruling, r1): a spec for a popular dependency that passes formal verification = the bar; no per-family threat model or extra security property set is in scope.
- Library entry (user ruling): both, mapped — a spec = the secure behaviour contract (e.g. strict RFC 4648 base64) + per-package profiles stating where each real package (npm `base64-js`, Python stdlib, …) deviates. A package without deviations matches the contract; deviations are named, never hidden.
- Publish rule (user ruling, orientation; supersedes r1 "every op's agreement"): a profile publishes once its exact relation is proven — fvdep's Lean model of the package = the contract with the named deviations applied, over the declared domain (statement built by fvdep, never a tagged theorem) ⇒ agreement on every input no deviation changes. Proofs are about the model; model ↔ real package = test evidence. Profile scope (user ruling): the listed operations, each with its own status; the profile shows the package API it does not cover.
- Spec modularity (user ruling): modular specs — each operation (e.g. `base64.encode`, `base64.decode_url`) = its own versioned spec module; consumers pin the modules they use; no shared per-dependency version line.
- Automation (user ruling): agent drafts, kernel admits — agents pick popular packages, draft spec + proofs from the standard + upstream tests; admission = Lean kernel build + axiom audit, fully proven entries alone; human spec review optional. Runs on vflab.
- Host (user ruling, fvapi commit 42c5b62): fvdep shares vflab with fvapi at equal priority — same `eturkes` account + `fvapi_gate.slice` for builds, checks + library growth; live services run outside the slice + outrank dev work; host maintenance announced to the fvapi session first. Conventions + paths = `CLAUDE.local.md`.
- Openness (user ruling): open core — popular specs public (repo licence Apache-2.0); paid = update feed/alerts, requested specs, built implementations. Licence label (MAIN): `LICENSE` has carried the LLVM exceptions since the repo's first commit ⇒ package metadata = SPDX `Apache-2.0 WITH LLVM-exception` (labels follow the published file; dropping the exception = the user's call).
- fva + fvtrace dependencies → fvdep (user: "eventually") → `.agent/deferred.md`.
- Library audit (MAIN): an obligation's status counts only after the verification profile's kernels replay the library — `debug.skipKernelTC` forgeries pass `#print axioms` with std axioms alone.
- Profile shape (MAIN): profile id `<eco>:<pkg>@<pkgver>[#<variant>]` (variant = one named configuration), entry versions per (area, id) (a revision = a new version); profile = Lean model of one package version (identity: artifact, runtime, options; per-call options = distinct operations) + per listed operation: contract id@version, domain, representation adapters, ordered deviations (Domains + deviation algebra); fvdep builds each operation's exact-relation statement; operation status published iff proven, else preview: the library entry lists the proven operations, a preview entry of the same id holds the rest, `list` + `show` print each operation's status; model ↔ real package = differential evidence (`fvdep profile --check`), never a proof.
- Module updates (MAIN): a registry `compat` declaration (statement `new spec = old spec` built by fvdep, proof in phase 2) ⇒ "same behaviour; proofs carry over": `upgrade` transports the existing proof (fvdep-generated `Eq.trans` module in phase 2, judged like any proof); no compat ⇒ minor = "compatibility not stated", major = "prove again". A proven `new = old` decides behaviour compatibility whatever the version labels say. Module dependencies (`uses`) = spec references, not implementation requirements.
- C-library delivery (MAIN): shape `abi` statement `@impl = Fvdep.Abi.V1_0_0.<shape> @spec` (`docs/library.md`); `fvdep build-lib` (needs the module DELIVERED) builds the C library from the receipt's phase-1 outputs (cache miss → rebuilt in a fresh sandbox, export digest must equal the receipt's) + writes a build record beside it, project files untouched; each example binding's differential run vs the spec oracle = glue evidence (mismatch ⇒ not delivered); trusted beyond the kernels: Lean compiler + runtime, C shim, binding — printed with every such delivery claim.
- Preview area (user ruling, orientation; supersedes r2 admission reading): the admitted library holds contract modules + profiles that meet every proof requirement; a preview (profile short of its publish proofs) stays visible + labeled in a separate preview area, never a library entry or coverage.
- Proof policy (user ruling, orientation): "proof required" = a saved project setting, on by default for every module; lock, upgrade + automation follow it; a development mode also accepts test evidence, labeled not delivered. A failing check or policy leaves manifest + lock byte-identical (MAIN). The lock records each module's receipt (Data formats); `check`, `lock` + `upgrade` judge the fresh result, `status` the lock receipts; `delivered` is derived at read time, never stored; any change of the checked closure or verification profile ⇒ stale ⇒ recheck before a delivery claim (MAIN).
- Obligation status derived from `#print axioms` (std axioms only = proven, `sorryAx` = open, other = trusts X), never hand-written; spec completeness (open obligations) + implementation evidence stay separate labels.
- Self-verification (user ruling, orientation): "As much of this system as would be considered feasible" is formally verified ⇒ every fvdep-owned component carries machine-checked proofs unless proving it is infeasible; each trusted residue (minimum: OS, Lean compiler + runtime, external tools fvdep runs) is named with its reason wherever a result is claimed.
- Retraction (user ruling, orientation): published versions are immutable; a retraction notice (reason + replacement version if one exists) is appended, never edited in; a retracted module no longer counts as delivered; its old proofs stay replayable as history and count only under the current checking rules.
- Launch set (user ruling, orientation): at IMPLEMENT close the library holds base64 (encode, decode, encode_url, decode_url) + semver (parse, compare) rebuilt under IMPLEMENT rules; the 4 prototype profiles re-checked → published or preview by these rulings; the proven base64 C library + Rust/Python/Node bindings as the example; + ≥1 new package admitted through the growth system on vflab, its run + any help recorded.
- Growth (user ruling, orientation): a scheduled job on vflab picks the next eligible package from a recorded popularity ranking (e.g. npm downloads, last 7 available days) + a queue the user adds to; a daily time budget caps agent work; each attempt records inputs + result. The drafting agent runs on the user's Claude subscription login stored on vflab (unattended); customer work never uses it.
- Updates (user ruling, orientation): the public library repo = the feed, with a machine-readable index of versions + retractions; `fvdep outdated` shows new versions, proven compatibility, retractions + the time of its last successful fetch; a failed fetch reports as failed, never "up to date". Paid alerts + signed releases → `.agent/deferred.md`. Requests (user ruling): not in this phase → `.agent/deferred.md`.
- Scan (user ruling + MAIN, orientation): reads exact resolved versions from lock files (e.g. `pnpm-lock.yaml`, `Cargo.lock`, `uv.lock`), direct + indirect dependencies apart, unresolved ranges labeled; a dependency counts as covered only when a profile exists for its exact resolved version + configuration (configuration the lock file does not record ⇒ `conditional`, printed with its assumptions, never covered); another version's profile = a suggestion.
- Readings (navigator-5/6/7 agree; MAIN): "provably secure" = formal correctness against the declared contract (Security bar); spec ↔ standard fidelity = separate evidence, never implied by proofs. "Any way they want" = any algorithm + representation in Lean (proofs: any Lean); other languages consume the proven code through the C library; native implementations = development evidence. Claims never exceed proofs: "published" names its op scope + measured package identity (artifact, runtime, options); "delivered" names its trusted base.
- C ABI (MAIN, orientation): exports pass lossless (pointer, length) buffers over the contract's whole declared domain; any narrower domain is explicit + modelled in the statement.
- Stack (MAIN, IMPLEMENT orientation; supersedes the prototype's speed pick): Lean 4.35.0 throughout — library (contracts, models, proofs), tool `fvdep` (proven pure core + thin IO interpreter), growth job `fvdep-grow`; non-Lean only where the product needs it: C ABI shim + example bindings (Rust, Python, Node), HACL* SHA-256 C (verified upstream) behind FFI, gate + CI + test drivers (bash, stdlib Python). - Conformance method (MAIN; supersedes the prototype's one-phase check): two phases. (1) Manifest per module: id@version, shape (`fn` | `abi`), implementation modules, proof modules, implementation constant, proof constant (`docs/interface.md` §7). (2) Implementation profile (versioned): before any build a trusted in-process parse checks every implementation module against a positive allowlist of syntax kinds over the whole tree (commands, terms, tactics, attributes, options); imports ⊆ Init, Std, the fvdep library + the manifest's implementation modules; reserved module prefixes refused (`docs/library.md`); an unlisted kind ⇒ NOT PROVEN naming file:line + kind. Property: accepted source ⇒ phase 1 runs toolchain + fvdep code alone (no consumer macro, metaprogram, build-time hook, `implemented_by`, `extern`, `unsafe`, `partial`, `opaque`) ⇒ its exports + compiled C denote the checked term (assumption: Lean parser, elaborator, compiler). v1 freezes once the launch example implementations (base64 ×4 incl. `abi` variants, semver ×2: structures, instances, well-founded recursion) pass it; each extension = new version + requalification + adversarial regressions. Proof modules: any Lean. (3) Phase 1 builds the implementation closure in a fresh sandbox (bwrap direct, no network, writes confined, deadline) against the pinned library with an fvdep-written build config; outputs hashed + frozen; its export = trusted. (4) Challenge = trusted spec + phase-1 export + the statement built as an `Expr` from registry constants (`@impl = @spec` | `@impl = Fvdep.Abi.V1_0_0.<shape> @spec`), no definition hole; theorem: the built type is that equation. (5) Phase 2 builds proof modules (any Lean, pinned deps) in a fresh sandbox; its export = untrusted. (6) Judge = statement + full constant graph (implementation constants included) vs the challenge + verification profile. (7) Supervisor isolation in every phase (consumer checks, library admission, growth): supervisor outputs, configs + exports outside every consumer-writable path; later phases get read-only binds; snapshots refuse links + special files. (8) Delivered C library = phase-1 outputs alone; its build record (`build-lib`) names library, header, ABI shape, shim + the receipt it extends; bindings = the consumer's glue, named as trusted. (9) The proven core maps the evidence record to verdict + lock action. Acceptance: forged kernel term, tampered vendored spec, `implemented_by`/`extern` swap, `native_decide` axiom, macro hijack of the statement, build-time C rewrite inside the implementation closure, link plant by proof build code, implementation module named like a spec module ⇒ NOT PROVEN; build code escaping the sandbox ⇒ no write outside it; an honest implementation ⇒ PROVEN.
- Verification profile (MAIN): versioned; required kernels Lean default, con-leche `--verified` (machine-checked consistency theorem for that mode), NanoDa (independent implementation) — each alone, sandboxed, with a deadline; PROVEN iff all accept + axioms ⊆ {propext, Classical.choice, Quot.sound}. Kernel status ∈ accept | reject | crash | timeout | decline (unsupported feature, reported apart from reject); sandbox or tool setup failure = infrastructure (exit 2), never a verdict. Pins toolchain + kernel binary digests + modes, export format, axiom set, deadlines, implementation-profile version + a canary corpus (known-good + known-false incl. a forged term), run at profile qualification + in the gate. v1 is qualified on the launch closures + canaries; a decline there → a MAIN ruling recorded here. Measured (descriptive, desktop n=3, 17.4 MB export): Lean 12.2 s, con-leche 9.7 s (2 jobs), NanoDa 5.2 s.

- Library API v1 (MAIN): launch-set ids, Lean modules, spec constants + types, shared type modules, C ABI shapes + registry format = `docs/library.md` (public; immutable once published); bodies + obligations = the library unit.
